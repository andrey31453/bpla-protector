# Правила проекта — ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ

## 0. Git: публикация — только по команде закрытия тикета

**По умолчанию агент ничего не публикует.** Обычная работа заканчивается локальными файлами в рабочем дереве. Пуш ветки, PR в `main` и его мерж — отдельная процедура, которую агент выполняет **только по явной команде владельца закрыть тикет** («всё хорошо, закрываем тикет») — см. п.0.2. До этой команды ни пуш, ни PR, ни мерж не выполняются, даже если работа выглядит законченной.

Запрещено всегда, без исключений:

- переписывание истории и силовые операции: `git push --force`, `-f`, `--force-with-lease`, `git push --mirror`, `--all`, `--tags`, `git push origin --delete <ветка>`, `git reset --hard` по опубликованным коммитам, `git rebase` / `git commit --amend` по уже опубликованным коммитам, `git filter-branch`;
- пуш напрямую в `main` и пуш в чужие ветки: свою ветку вводит в `main` только PR по процедуре п.0.2;
- работа с remote и чужими ветками на удалённом репозитории: создание/удаление/переименование удалённых веток, смена upstream, `git remote add/set-url/rename/rm`, `git config --global` для remote;
- публикации и деплой в обход процедуры: `npm publish`, `gh-pages`, `gh release create`, `gh workflow run`, ручной запуск `.github/workflows/deploy-pages.yml`, прямые вызовы Pages/деплой-API и `gh api .../merges`, `.../dispatches`, `.../git/refs`.

Почему осторожно: пуш в `main` запускает GitHub Actions `.github/workflows/deploy-pages.yml`, который собирает все сайты и публикует `saits/_site` на GitHub Pages. То есть мерж в `main` — это сразу выкладка в боевой сайт.

Разрешено всегда, без спроса:

- безопасные локальные команды: `git status`, `git diff`, `git log`, `git show`, `git branch --show-current`, `git fetch`, `git pull --ff-only` в своей ветке, `git stash` (аккуратно — см. п.0.1);
- `git add` и `git commit` — по прямой просьбе пользователя; в процедуре закрытия тикета коммит входит в шаг 1 (п.0.2).

Разрешено только по команде закрытия тикета: `git push` своей ветки, `gh pr create`, `gh pr merge` — строго в порядке шагов п.0.2.

### 0.1 Параллельная работа: в репозитории есть второй агент — у каждого своя ветка

В этом же GitHub-репозитории параллельно работает второй агент, но из другой папки (другая рабочая копия репозитория). Чтобы мы не затирали работу друг друга, каждый агент ведёт работу в своей отдельной ветке и не трогает чужую папку и чужую ветку. Всё, что ниже, действует так же строго, как п.0 и п.1.

Правила:

- Перед началом работы проверь свою ветку: `git branch --show-current`. Работай только в своей ветке; имя своей ветки выбирай сам случайно пользователю все равно (например `agent-<короткий случайный суффикс>-<тема>`), создать её из `main` можно так: `git switch -c agent-7d2a-тема`.
- Работа считается закреплённой в своей ветке **только после коммита в неё** (`git add` + `git commit` — по прямой просьбе пользователя). Незакоммиченные правки живут в рабочем дереве и «переезжают» вместе с тобой при переключении веток, поэтому их легко случайно утащить в `main` или к чужим изменениям. Если правка уже сделана на `main` — не бросай её там: заведи свою ветку от `main` и перенеси работу в неё.
- СТРОГО ЗАПРЕЩЕНО переключаться на чужую ветку (`git switch`, `git checkout <ветка>`) и делать в ней любые коммиты и правки.
- СТРОГО ЗАПРЕЩЕНО трогать чужие ветки: `git branch -d/-D`, `git merge`, `git rebase`, `git cherry-pick`, `git revert`, `git reset` по чужим веткам, `git push` в них.
- Не переписывай общую историю: никаких `git rebase`, `git commit --amend`, `git filter-branch`, force-операций в общей ветке `main`.
- Свою ветку в `main` вводит только PR по процедуре п.0.2 — по команде закрытия тикета. Чужие ветки не сводятся и не трогаются никогда: ни `merge`, ни `rebase`, ни `cherry-pick`, ни мерж их PR.
- Аккуратно с командами, затрагивающими незакоммиченные изменения (`git stash`, `git restore`, `git checkout -- .`, `git clean -fd`, `git reset --hard`): к чужому рабочему дереву их не применять, а у себя — только по явной просьбе пользователя.
- Публикация — только для своей ветки и только по процедуре п.0.2 (по команде закрытия тикета). Чужую ветку не публикуем никогда.

### 0.2 Процедура: pull перед задачей и закрытие тикета

#### Перед началом любой задачи

1. `git branch --show-current` — убедись, что ты в своей ветке (не в `main` и не в чужой). Если ветки ещё нет, создай её от актуального `main`: `git fetch origin` → `git switch -c agent-<суффикс>-<тема> origin/main`.
2. `git pull --ff-only` — подтяни свою ветку с remote. Работу не начинай, пока pull не прошёл.
3. Если pull ругается на расхождение веток — ничего не форсируй: остановись и спроси владельца.
4. Если ветка отстала от `main`, подтяни актуальный `main` **в свою ветку** обычным merge: `git fetch origin` → `git merge origin/main`. `main` и чужие ветки при этом не трогаются.

#### Закрытие тикета — только по явной команде владельца

Триггер — прямая фраза владельца: «всё хорошо, закрываем тикет», «закрываем», «можно публиковать». Без такой фразы шаги ниже не выполняются, даже если работа закончена.

1. Убедись, что работа закоммичена в свою ветку; незакоммиченные правки закоммить: `git add <файлы>` → `git commit -m "<сообщение>"`.
2. `git pull --ff-only` в своей ветке — забрать свежее с remote.
3. `git push -u origin <своя ветка>` — пуш только своей ветки.
4. Создай PR в `main`: `gh pr create --base main --head <своя ветка> --title "<заголовок>" --body "<описание>"`.
5. Проверь конфликты с `main`: `gh pr view --json mergeable,mergeStateStatus` или локально `git fetch origin` → `git merge-tree --write-tree origin/main HEAD` (дерево без конфликтных маркеров = чисто).
6. Конфликтов нет — мержи PR: `gh pr merge --merge` (или `--squash`, если так принято у владельца). Конфликты есть — **остановись**, ничего не мержи, покажи владельцу список конфликтных файлов и жди решения.
7. Вернись на `main` и подтяни его: `git switch main` → `git pull --ff-only`.
8. Отчитайся: номер PR, хеш мерж-коммита, что теперь в `main`, и напомни, что пуш в `main` запустил выкладку Pages.

Ограничения процедуры: мерж в обход конфликтов и `gh pr merge --admin` не применять; чужие PR и чужие ветки не трогать; ветку после мержа не удалять без отдельной просьбы владельца; деплой вручную не запускать — он стартует сам от пуша в `main`.

## 1. Изоляция сайтов — СТРОГО ЗАПРЕЩЕНО нарушать

В папке `saits/` хранится несколько РАЗНЫХ сайтов на одну тематику: `saits/sait-00`, `saits/sait-01`, `saits/sait-02` ... `saits/sait-XX`.

При работе над ЛЮБЫМ `saits/sait-XX`:

- СТРОГО ЗАПРЕЩЕНО читать, листить (`ls`, `glob`, `read`), искать (`grep`, `search_codebase`) и открывать любые другие папки `saits/sait-YY`, где `YY != XX`.
- Считай что других `saits/sait-YY` НЕ СУЩЕСТВУЕТ. Не проверяй их наличие, не сравнивай, не копируй оттуда дизайн, тексты, структуру, компоненты, стили.
- `search_codebase` и любые поиски по репозиторию выполняй ТОЛЬКО внутри `saits/sait-XX` + `docs/` (см. п.2). Никогда не делай поиск по корню `/` или по `saits/` целиком.
- Каждый новый сайт должен быть УНИКАЛЬНЫМ: другая структура блоков, другая палитра, другая типографика, другие формулировки. Копирование с соседних сайтов — нарушение ТЗ.

Исключение: можно посмотреть `saits/README.md`, `saits/build.sh`, `saits/dev.sh` — это общие скрипты.

## 3. Как создавать новый сайт `saits/sait-XX`

- Работай только внутри своей папки `saits/sait-XX`.
- Не заглядывай в соседние `saits/sait-YY` ни под каким предлогом (даже "для примера" или "чтобы не повторяться" — просто делай по-другому, не глядя).
- Если нужно переиспользовать логику сборки — смотри только `saits/build.sh` / `saits/dev.sh`.
- Определи продуктовую линию сайта (см. п.2) и бери контент из её материалов: для линии A — `docs/texts/01-…09-…` и `preza.md`, для линии B — `docs/texts/zpb/`. Линии можно совмещать в одном сайте, каталоге и разделе — они дополняют друг друга.
- Если в промпте сказано смотреть ТЗ директолога — при создании сайта ориентируйся на ТЗ директолога: `docs/Запросы для лендингов.txt`. Оно имеет важное значение, но без прямого указания рассматривай его просто как ещё один источник информации.

### Технологии (если не указано иное)

- **Tailwind CSS** — для стилизации.
- **Nunjucks** — для композиции разметки на этапе сборки. Обязательно при создании нового сайта и при переводе существующего сайта в рабочее состояние — см. п.4.
- **Ванильный JS** — без фреймворков; только прогрессивное улучшение, без генерации контента — см. п.4.
- **Локальные картинки** — только из `docs/images/`. Если нужны новые изображения, сначала подгрузи их в `docs/images/`.

### Требования к стилистике

- **Заголовки** — без точки в конце.
- **Дизайн-приёмы, токены, типографика, состояния и доступность** — по локальному киту UX/UI Agent Skills (см. п.6): это обязательная база для новых страниц и переделки существующих.

## 4. Композиция разметки и единый источник данных — ОБЯЗАТЕЛЬНО

Правила ниже действуют **при создании нового `saits/sait-XX`** и **при переводе уже существующего сайта в рабочее состояние** (переделке/переписывании).

Речь только о композиции разметки и о данных. Способ стилизации п.4 не меняет: как и раньше — **Tailwind CSS** (п.3).

### 4.1 Повторяющаяся разметка — только через Nunjucks на этапе сборки

Композиция выполняется **шаблонизатором Nunjucks во время сборки**: в `dist/` попадает обычный статический HTML, никакого фреймворка и никакого JS-рендера на клиенте.

- Общие куски разметки выносятся в шаблоны и больше в страницах не дублируются:
  - `src/layouts/` — скелет страницы (`base.njk`: `doctype`, `head`, `header`, `<main>`, CTA, `footer`, JSON-LD, подключение JS/CSS);
  - `src/partials/` — блоки (`head`, `header`, `footer`, `cta`, `breadcrumbs`, `page-hero`, `jsonld`);
  - `src/macros/` — повторяемые элементы с параметрами (`card`, `kpi`, `faq`, `note`, `chip`).
- Страницы в корне сайта (`index.html`, `ugrozy.html`, …) — тонкие обёртки: только `{% extends "layouts/base.njk" %}` и своё уникальное содержимое в `{% block content %}`. Восемь одинаковых `<head>`/`<header>`/`<footer>` в восьми файлах — нарушение.
- Списки (меню, карточки, FAQ, крошки) разворачиваются циклом `{% for %}` по JSON-данным (см. 4.2), а не копипастой.
- **СТРОГО ЗАПРЕЩЕНО** рисовать контент, навигацию или любые ссылки из JS: `innerHTML`, `document.write`, `fetch()` шаблонов, клиентский роутинг, Web Components с Shadow DOM для контента. Причина — SEO: контент и ссылки обязаны присутствовать в отданном HTML.
- **JS — только прогрессивное улучшение**: модули в `src/js/modules/`, инициализируются по `data-*`-хукам, ничего не рендерят, а только переключают классы/атрибуты (мобильное меню, аккордеон, reveal, маска телефона, отправка формы). Реестр модулей — в `src/js/main.js`, каждый модуль в `try/catch`, чтобы падение одного не ломало остальные.
- Reveal-анимации не должны скрывать контент при отключённом/упавшем JS: базовое состояние — видимо, `opacity: 0` включается только при наличии класса `js` на `<html>` (класс ставит крошечный инлайн-скрипт, `no-js` → `js`).
- Каждый H1, заголовки, `<title>`, `description`, хлебные крошки, `sitemap.xml` и JSON-LD формируются из данных на сборке — не из JS.
- Совместимость со сборкой репозитория обязательна: `npx vite build --base=./` (то, что вызывает `saits/build.sh`) должен работать без правок общих скриптов; внутренние ссылки пишутся как `/ugrozy.html`, `saits/fix-paths.mjs` переводит их в относительные для GitHub Pages.
- Новые зависимости допустимы только как build-time devDependency (например `nunjucks`); количество клиентских зависимостей — ноль.

### 4.2 Все повторяющиеся данные — в JSON, один факт в одном месте

Любое значение, которое встречается больше одного раза (телефон, e-mail, адрес, реквизиты, название бренда, домен, пункты меню, список страниц, `title`/`description`, карточки товаров), обязано лежать в `src/data/` и подставляться в шаблоны. Хардкод в разметке запрещён.

| Файл                     | Что хранит                                                                                                 | Куда попадает                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `src/data/site.json`     | Бренд, телефон (+ `href` для `tel:`), e-mail, адрес, режим работы, домен `baseUrl`, OG-картинка, цвет темы | `header`, `footer`, CTA, контакты, `<link rel="canonical">`, OG/Twitter, JSON-LD                                |
| `src/data/pages.json`    | Список страниц: `slug`, пункт меню, `title`, `description`, `priority`/`changefreq`, флаги `noindex`       | Меню, хлебные крошки, `<title>`/`description`, canonical, `sitemap.xml`, `robots.txt`, JSON-LD `BreadcrumbList` |
| `src/data/products.json` | Каталог изделий/услуг: название, краткое описание, характеристики, ссылка, изображение                     | Каталог, карточки, `ItemList`/`Product` в JSON-LD                                                               |
| `src/data/*.json`        | Любые другие повторяемые списки (FAQ, преимущества, этапы, характеристики, сценарии)                       | Соответствующие блоки страниц                                                                                   |

- Телефон, e-mail и адрес в `header` и `footer` — это **один** источник (`site.json`), а не два разных места в разметке.
- Добавление новой страницы = одна запись в `pages.json`; при этом автоматически появляются пункт меню, запись в `sitemap.xml` и хлебные крошки. Дублировать её в разметке не нужно.
- SEO-мета на каждой странице уникальна и берётся из `pages.json`; одинаковых `title`/`description` на разных страницах быть не должно.
- Значения, зависящие от площадки/домена, также берутся из `site.json` — чтобы сайт можно было перенести на другой домен правкой одного файла.

### 4.3 Типовая структура сайта

```
saits/sait-XX/
├─ index.html  ugrozy.html  ...          # входы Vite: {% extends %} + уникальные блоки
├─ vite.config.js                        # MPA-входы, порт, плагин Nunjucks

```

- Шаблоны, данные, стили и тексты живут **только внутри своего `saits/sait-XX`** — изоляция и уникальность из п.1 действуют в полном объёме. Нельзя брать partials, палитру или данные из соседнего сайта.
- Общим в `saits/` может быть только переиспользуемый «движок» сборки (плагин Nunjucks, хелперы) — и то не дизайн и не контент. Если движок появляется, он лежит отдельно (например `saits/_engine/`) и не подменяет уникальные `partials/styles/data` сайта.

## 5. ТЗ директолога: структура лендингов и запросы — `docs/Запросы для лендингов.txt`

Источник — `docs/Запросы для лендингов.docx` (текстовая версия: `docs/Запросы для лендингов.txt`, сконвертирована без потери слов, порядок абзацев и таблицы сохранены). Это ТЗ от специалиста по контекстной рекламе: под какие поисковые запросы делать лендинги и из каких блоков их собирать.

- Это **карта страниц и структура лендингов**: темы, состав блоков и их порядок. Цифры, характеристики и формулировки по продукту берём из источников п.2 — своё не выдумываем.
- Наша задача — **один большой сайт, внутри которого несколько лендингов**. Лендинг — отдельная страница сайта (`index.html` + по странице на тему), у каждой свой `slug`, `title`, `description` в `pages.json` (п.4.2). Отдельных сайтов под каждую тему не делаем.
- Блоки страницы идут в порядке из ТЗ; блоки, помеченные автором как «не уверена, что нужно» (например нормативная база), по умолчанию включаем — для B2B-аудитории они усиливают доверие; если заказчик решит иначе, блок отключается.

### 5.1 Сколько лендингов рекомендует ТЗ

Формулировка ТЗ: «Под запросы желательно сделать несколько лендингов». Всего 5 тем — это **5 лендингов внутри одного сайта, а не 5 отдельных сайтов**. Из них 4 расписаны по блокам, 1 (окна) директолог оставил на уточнение у заказчика — эту тему расписали мы сами: `docs/lendingi/05-zashchita-okon.md` (22 блока по каркасу 5.2).

| --- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Защита окон и остекления (включая рольставни)             | в ТЗ структура не расписана: «надо уточнить у заказчика». Наша структура — `docs/lendingi/05-zashchita-okon.md`; минимум из ТЗ (товар и его типы, сертификаты и испытания, услуги, документация, гарантия, примеры работ, клиенты, минимальная стоимость работ) в ней учтён |

Если темы нет в ТЗ или она в нём не расписана — структуру разрабатываем сами в `docs/lendingi/` по каркасу 5.2 и не блокируем работу ожиданием согласования: лишняя страница сайту не вредит, а правки потом вносятся в данные страницы. Факты и цифры при этом всё равно берём только из источников п.2.

### 5.2 Типовой каркас лендинга по ТЗ

1. Первый экран (Hero): УТП-заголовок, подзаголовок, бейджи/цифры, регион работы, CTA («Запросить расчёт» / «Заказать звонок»)
2. Почему объект уязвим (проблема и специфика именно этого типа объекта)
3. Что именно защищаем (таблица «узел объекта → что закрываем → специфика решения»)
4. Типы защитных конструкций
5. Ключевые инженерные ограничения (таблица «ограничение → что означает → как соблюдаем»)
6. Материалы (сравнительная таблица: СВМПЭ / кевлар-арамид / стальной трос / полиамид) + блок «почему не используем полипропилен и поликарбонат» + краткая формулировка для лендинга
7. Состав работ / Услуги (обследование → проектирование → согласование → изготовление → монтаж → сервис)
8. Нормативная база
9. Уровни защиты по СП 542 (таблица 1–4-й уровень)
10. Категорирование объекта (для подстанций и ТЭК)
11. Сертификаты и результаты испытаний, гарантия
12. Примеры работ — кейсы по схеме «объект → задача → решение → сроки → результат (фото до/после)», 2–4 кейса достаточно
13. Клиенты (логотипы + 1–2 развёрнутых отзыва с ФИО и должностью)
14. Документация по итогам работ (проект ЗОК, паспорт изделия, акты, протоколы, сертификаты)
15. Участие в тендерах (ЭТП, 44-ФЗ, 223-ФЗ, помощь в подготовке ТЗ заказчику)
16. Стоимость (ориентиры «от N ₽/м²» + что влияет на цену + CTA на расчёт)
17. FAQ (вопросы из ТЗ, в том числе про свет, эвакуацию, РЭБ, исторические объекты)
18. Финальная форма заявки / контакты (поля под тип объекта и регион)

### 5.3 Что ещё зафиксировано в ТЗ

- Ориентиры цен из документа: мосты — материалы от 370 до 2600 ₽/м², полный комплекс от 2500 ₽/м²; здания — под ключ от 4500–6500 ₽/м² (цифры даются как ориентир с оговоркой «зависит от объекта»).
- Нормативная база, на которую ссылается ТЗ: СП 542.1325800.2024, ФЗ № 256-ФЗ, ФЗ № 151-ФЗ от 25.05.2026, Указ Президента РФ № 604 от 24.08.2026, ПП РФ № 459, СП 155.13330, 123-ФЗ, ГОСТ Р 59789, ГОСТ 9.307, ПП РФ № 1046, ПП РФ № 258 (важно: ТЭК исключён из его действия).
- Требование к материалам: на взрывопожароопасных объектах горючие сетки запрещены (п. 9.2.3 СП 542), для резервуаров — только независимая схема (п. 6.3.1).
- Тон и позиционирование заданы в ТЗ: показывать понимание специфики конкретного типа объекта, а не «натягиваем сетку» / «общая защита от дронов».

### 6.3 Базовые дизайн-требования — действуют всегда, без чтения кита

1. **Один источник правды.** Цвет, типографика, отступы, радиусы и длительности живут в токенах сайта (Tailwind v4 `@theme`); хардкода `#hex`, `px`, `ms` в разметке и стилях нет. Смена палитры — правка одного файла.
2. **Контраст не ниже WCAG 2.2 AA:** 4.5:1 для обычного текста, 3:1 для крупного (от 24 px или от 18,66 px полужирного) и для границ/иконок интерфейса. Проверяется скриптом, а не «на глаз».
3. **Состояния интерактивных элементов:** default, hover, focus (видимое кольцо), active, disabled; у полей ещё error, у асинхронных кнопок loading, у выбираемых — selected.
4. **Один акцент на экран.** Крупный заголовок минимум в 2,5 раза больше основного текста; сетка из четырёх одинаковых карточек «без главного» — так не делаем, у экрана должна быть понятная первая точка внимания.
5. **Ноль эмодзи** в разметке, стилях, скриптах, текстах и в переписке: вместо них — инлайн-SVG (lucide) на `currentColor` или слова.
6. **Анимации уважают `prefers-reduced-motion`;** reveal-блоки не скрывают контент при отключённом или упавшем JS (п.4.1).
7. **Адаптив без горизонтального скролла** на 320–414 px: фиксированная ширина, которая не сжимается, — баг.

### 6.4 Гейты: числа только из запуска

Лёгкие проверки кита работают сразу (нужен только `python3`), их стоит прогонять перед сдачей сайта:

```
python3 local/skills/ux-ui-agent-skills/scripts/check_no_emoji.py saits/sait-XX/src

```

Тяжёлые гейты с реальным рендером (`scripts/verify_states.mjs`, `scripts/verify_responsive.mjs`, `scripts/accuracy_report.mjs`) требуют внутри папки кита `npm install && npx playwright install chrome`. Их ставят и запускают только когда это оправдано задачей; `node_modules` кита остаются локальными и не коммитятся.

Правило простое: **не называй число (контраст, «WCAG пройден», «все состояния ок»), если ты его не измерил.** Не запускал — пиши «не проверено».
